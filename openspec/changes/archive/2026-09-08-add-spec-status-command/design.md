# Design

## Context

The user's goal is smaller, resumable agent sessions per spec. The naive implementation — write progress
into a document — trades one token cost (a resuming agent's context-gathering) for another (every session
that touches the doc must also update it, and it silently goes stale the moment someone forgets). This
repo already relearned that lesson twice this week: `docs/governance.md`'s restated sections and
`plans/roadmap.md`'s status column both needed dedicated freshness mechanisms once written as prose. The
net token economy only improves if the progress view is computed, not recorded.

## Decisions

### A script, not a document

`scripts/spec-status.sh` computes its output at read time from two sources that already exist and are
already authoritative elsewhere in the repo:

- `openspec list --json` for `totalTasks`/`completedTasks` per active change — the same source
  `scripts/check-openspec-archive.sh` already trusts for completion state.
- Each active change's `openspec/changes/<name>/specs/*/` subdirectory names for the capability it touches
  — the same convention `openspec archive` uses to know which accepted spec to update.

No new file is written and no existing file needs a new field, so there is nothing for a freshness check
to keep in sync — the command cannot drift because it has no persisted state to drift from.

### Placed as a command, referenced from orientation, not embedded in it

`docs/repository-orientation.md` gets one short "Resuming Work" note telling an agent to run the script
before reading anything else, rather than a table of current progress. A table would need to be
regenerated by hand on every session; a pointer to a command does not.

### Multiple capabilities per change, multiple changes per capability

A change's `specs/` directory can name more than one capability (rare, but `openspec` allows a delta to
touch more than one accepted spec); the script lists the change once per capability it declares. Because
`openspec/changes/` excludes `archive/` for the active listing, only in-progress work appears — a
capability with no active change is simply absent from the output, which is the answer a resuming agent
needs: "is anything in flight here."

## Risks

- **`openspec list --json`'s schema changes.** Low: `check-openspec-archive.sh` already depends on the same
  two fields; a breaking change there would surface in the existing archive-completeness gate first.
- **A change's `specs/` directory is empty (documentation-only change with no delta spec).** The script
  skips it — a change with nothing to report about capability progress correctly produces no capability
  row.
