# Design: Add Project Rename Tooling

## Identity is read from `package.json`, not hard-coded, so the script is idempotent

A naive script would hard-code `OLD_NAME=<the-name-at-the-time-it-was-written>` (`agentic-boiler`, when
this script was first written). That breaks the moment it's run a second time (a fork owner renaming
twice, or a maintainer fixing a typo) because the second run finds nothing left matching the hard-coded
name to replace. Instead `scripts/rename-project.sh` reads the current name from `package.json`'s `"name"`
field (`package.json:2`) and the current owner from `repository.url`
(`git+https://github.com/<owner>/<name>.git`, `package.json:13`) at the start of every run. This makes the
rewrite a pure function of current-state -> new-state, so it is safe to re-run and safe to run on a fork
that already renamed once.

## Filename rewrite walks the tree once and renames deepest-first

`openspec/specs/spec-loop-governance/` is the one tracked directory whose name derives from the
project identity (confirmed by `grep -rn spec-loop` across the tree, excluding
`openspec/changes/archive/**`). The script does not special-case that path. Instead it finds every tracked
file/directory under the repo (via `git ls-files` plus directory names, excluding the same exclusion list
used for content) whose basename contains the old kebab-case name, and `git mv`s it, processing the deepest
paths first so renaming a parent directory doesn't invalidate a child path already queued for its own
rename. This keeps the script generic: a future template evolution that adds another
`<name>-something/` directory doesn't require touching the script.

## Content rewrite is a single `grep -rl` + `sed -i` pass over four fixed strings, not a templating engine

The four strings that need rewriting are: the kebab-case name (`spec-loop`), the npm scope
(`@spec-loop`), the GitHub owner (`salzayat`), and the derived title (`Spec Loop`, matched
case-sensitively so it doesn't clobber unrelated title-case text). Introducing a templating layer
(placeholders like `{{PROJECT_NAME}}`) was considered and rejected: it would require rewriting every
tracked file to use placeholders first, which is a bigger, riskier change than the fork-onboarding problem
calls for, and it would make the repository's own tracked files not directly runnable/readable outside the
templating step. Plain string substitution over the existing real values, scoped by an exclusion list, is
enough because the identity strings are distinctive (no other legitimate content in this repo's tracked
files contains `spec-loop` or `salzayat` as substrings outside the excluded archive) — with one
exception: `plans/roadmap.md:14` names the archived change `improve-agentic-boiler-governance` by its
literal directory id, and that id embeds the project name even though the directory itself must not be
renamed (archives are excluded). A blanket substitution would silently break that reference into
`improve-spec-loop-governance`, a change that doesn't exist. The script closes this by placeholder-swapping
every archived change's id (its directory name with the date prefix stripped) out before the generic
substitution and back in afterward, so a living file can name an archived change without that name being
treated as a live identity string.

All of the above — protection placeholders, the four identity substitutions, and their restoration — are
assembled into a single sed script and applied with one `sed -i` per file. An earlier draft ran three
separate `sed`/`cp`/`mv` passes per file, which silently reset the mode of any rewritten _executable_
tracked file (including `scripts/rename-project.sh` itself, since its own comments mention the old name) to
the umask default, because each intermediate `> newfile && mv` step creates a fresh inode instead of
editing in place. A single in-place `sed -i` preserves the original file's permission bits the way editing
it by hand would.

## `package-lock.json` is regenerated by `npm install`, not pattern-matched

`package-lock.json:2,8` embeds `"name": "spec-loop"` inside a generated dependency graph. Editing it
with `sed` risks producing a lockfile that's textually consistent but structurally stale (wrong resolved
hashes if npm's lockfile format changes). The script instead lets `sed` rewrite the four `package.json`
files (root plus `packages/hello`, `packages/greeter`) and then runs `npm install`, which npm regenerates
correctly from the edited manifests. This is also the step that proves "updating after forking still
works": if the renamed scope (`@<new-name>/hello`) doesn't resolve, `npm install` fails immediately instead
of leaving a silently broken workspace for the fork owner to discover later at build time.

## Upstream template tracking stays a documentation change, not new tooling

`TEMPLATE.md` currently has no guidance for a fork owner who wants to keep pulling improvements from the
upstream template repository after personalizing their fork. Building a merge-conflict-resolution tool for
that is out of scope (see Non-Goals in `proposal.md`). What the rename script controls is the _shape_ of
the diff it produces: because every rewritten line is a real content or filename change (no placeholder
round-trip) and the exclusion list keeps historical archive directories untouched, a future
`git merge upstream/main` only conflicts on the specific lines this script touched — which
`TEMPLATE.md`'s new "Track upstream template updates" section names explicitly, so the fork owner knows
those conflicts are expected and how to resolve them (keep the fork's renamed value).
