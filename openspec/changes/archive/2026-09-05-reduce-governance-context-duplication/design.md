# Design

## Context

Two categories of context load per agent session: the eagerly loaded `AGENTS.md` (via the `CLAUDE.md`
symlink, `CLAUDE.md -> AGENTS.md`), and the documents the workflow tells agents to read before editing —
the accepted specs (~20.6 KB across eight files) plus `docs/`. Token efficiency here is dominated by
duplication in the eager file and by agents over-reading the spec set, not by any single document being
too long.

## Decisions

### Trim the hand-written Nx section, not the auto-managed one

`AGENTS.md` contains two Nx blocks. The generic guidance (prefer `nx run`, prefix the package manager,
consult `nx_docs`, don't guess flags, use the `nx-workspace` skill) exists in **both** the hand-written
`## Nx Conventions` section and the auto-generated block delimited by `<!-- nx configuration start-->` /
`<!-- nx configuration end-->` (`AGENTS.md:88`–`AGENTS.md:100`). The auto block is regenerated by Nx
tooling on `nx` invocations, so deleting it is futile — it returns. Therefore the durable saving is to
trim the **hand-written** section down to only what the auto block does not cover:

- "Use the `nx-generate` skill first for scaffolding or project-structure changes" (repo workflow, not in
  the auto block).
- "Preserve explicit `lint`, `typecheck`, `test`, `build` targets for every project" (repo invariant, not
  in the auto block).

The `repository-documentation` requirement "Agent guidance is actionable and bounded" says `AGENTS.md`
MUST state Nx task conventions. After the trim, the conventions are still present — split between the two
retained repo-specific bullets and the auto-managed block — so the requirement still holds. This is why
the delta below _modifies_ that requirement to add a no-duplication clause rather than relaxing the
must-state clause.

### `docs/governance.md` points instead of paraphrases

The four restated sections in `docs/governance.md` (`docs/governance.md:8`, `:21`, `:30`, `:48`) are
guidance, and the accepted specs plus `AGENTS.md` are authority. Keeping a paraphrase in a guidance doc
invites drift. The unique, worth-keeping content is the _purpose_ framing (`docs/governance.md:3`) and the
concrete `check-docs.sh` freshness mechanism (`docs/governance.md:48`), which names the actual script and
the `CHECK_DIFF_RANGE`/Dependabot behavior confirmed at `scripts/check-docs.sh`. Everything else becomes a
one-line pointer to `AGENTS.md` and `openspec/specs/`.

### A spec index lowers per-task spec reads, the larger cumulative cost

The workflow's "read the relevant accepted specs before editing" sends agents into eight spec files with
no map from subject to file. A one-line-per-capability index at the top of
`docs/repository-orientation.md` (which the workflow already routes agents to) lets an agent open the one
governing spec directly. This is placed in orientation rather than a new file so it stays within the
document the `repository-documentation` "orientation" requirement already governs, and so `check-docs.sh`
already treats it as a doc.

## Risks

- **Drift between the index and the spec set.** If a capability is added under `openspec/specs/` without
  updating the index, the index misleads. Mitigation: the added requirement's scenario makes the index a
  documented obligation, and `check-docs.sh` already flags `openspec/*` changes that ship without a doc
  update — adding a spec touches `openspec/*` and thus prompts the orientation edit.
- **The auto-managed Nx block could later add a repo-specific bullet upstream.** Low impact: the trimmed
  hand-written bullets are additive and independent; a future duplication would be caught by the same
  no-duplication requirement on the next harness/doc review.
